\subsection{Multi-Dimensional Evaluation Harness}
\label{sec:method_evalharness}

\subsubsection{Judge Configuration via YAML}

\textcolor{blue}{The evaluation harness is configured independently from the runtime under test. A separate YAML file specifies the judge model, decoding parameters, and prompt templates for each scoring function. This separation is intentional. It allows a stronger or more stable model to serve as the judge, and it lets researchers redefine the evaluation criteria without editing the evaluation code. In practice, we recommend using a deterministic judge configuration with temperature fixed at zero so that repeated runs remain comparable.}

\subsubsection{Configurable Evaluation Metrics}

\textcolor{blue}{EABench combines judge-based metrics with deterministic diagnostics. The assertion score measures factual coverage by checking whether the final answer satisfies the case assertions. Tool-search-result relevance measures whether the tools selected by the agent and the evidence they returned were appropriate for the query. Response-citation score measures whether the final answer cites real, relevant artifacts and uses a well-formed references section. These judge-based metrics are complemented by deterministic counts for retrieved evidence items, citations, latency, token usage, and tool calls. Because the prompt templates and thresholds are defined in YAML, researchers can extend the metric set or tighten the evaluation criteria without changing the harness logic.}

\subsubsection{Pass/Fail Criteria}

\textcolor{blue}{A case is marked as passed only when two conditions hold simultaneously: the assertion score exceeds a correctness threshold and the response-citation score exceeds a grounding threshold. This dual criterion encodes an important design principle. A response that sounds plausible but cites hallucinated artifacts should fail, and a fully cited response that does not answer the question should also fail. EABench therefore treats correctness and grounding as jointly necessary conditions for enterprise-agent success.}

\subsubsection{Side-by-Side Comparison and Diagnostics}

\textcolor{blue}{For comparative studies, EABench can evaluate two agent configurations on the same case and ask a judge model to declare a winner. These pairwise judgments support win-rate analyses and Bradley--Terry modeling, while the underlying per-case metric vectors support paired tests such as the Wilcoxon signed-rank test. Because the result structure stores the full response, tool trace, assertion outcomes, and citation logs, comparative findings are accompanied by diagnostics that explain why one agent won rather than only whether it won.}

\subsubsection{User-Level Experience Simulation}

\textcolor{blue}{Evaluation is always grounded in a requesting user context. Before each case is run, the search engine is bound to \texttt{case.user\_id}, and access-control rules are enforced consistently across search results, citation verification, and debugging views. This design allows the same tenant to support engineer, manager, and contractor personas without maintaining separate corpora, and it turns access control into a benchmarked capability rather than an external precondition.}
